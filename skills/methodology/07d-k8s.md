## RBAC

### Attack Surface

Kubernetes RBAC misconfigurations are the most common cluster-level vulnerability. `cluster-admin` bindings on service accounts or user groups grant unrestricted cluster access. Default service accounts in namespaces may have auto-mounted tokens with excessive permissions. Wildcard verbs (`*`) or resources (`*`) in Roles and ClusterRoles create overprivileged identities. Stale bindings for deleted users or decommissioned services leave orphaned access paths.

### Verification Commands

```bash
# List all ClusterRoleBindings (look for cluster-admin and wildcard bindings)
kubectl get clusterrolebindings -o json | \
  jq '.items[] | select(.roleRef.name == "cluster-admin") | {name: .metadata.name, subjects: .subjects}'

# List all ClusterRoles with wildcard verbs or resources
kubectl get clusterroles -o json | \
  jq '.items[] | select(.rules[]? | (.verbs[]? == "*") or (.resources[]? == "*")) | .metadata.name'

# Check default service account tokens in each namespace
kubectl get serviceaccounts --all-namespaces -o json | \
  jq '.items[] | select(.automountServiceAccountToken != false) | {ns: .metadata.namespace, name: .metadata.name}'

# List RoleBindings in a specific namespace
kubectl get rolebindings -n NAMESPACE -o json | \
  jq '.items[] | {name: .metadata.name, role: .roleRef.name, subjects: .subjects}'

# Check what a specific service account can do
kubectl auth can-i --list --as=system:serviceaccount:NAMESPACE:SA_NAME

# Check for privilege escalation paths (create pods, exec, secrets access)
kubectl auth can-i create pods --as=system:serviceaccount:NAMESPACE:SA_NAME
kubectl auth can-i create pods/exec --as=system:serviceaccount:NAMESPACE:SA_NAME
kubectl auth can-i get secrets --as=system:serviceaccount:NAMESPACE:SA_NAME
kubectl auth can-i create clusterrolebindings --as=system:serviceaccount:NAMESPACE:SA_NAME
```

### Evidence Logging

```bash
ensphere evidence log \
  --probe-type cloud_k8s --technique cli_verification \
  --url "k8s://CLUSTER/clusterrolebinding/BINDING_NAME" \
  --result confirmed --session 7 \
  --file ./ensphere-pentest/07-cloud/evidence.jsonl \
  --notes "ClusterRoleBinding grants cluster-admin to default service account in namespace 'app'"
```

## Pod Security Standards

### Attack Surface

Pods running as root, with privileged containers, or with `hostPID`/`hostNetwork`/`hostIPC` enabled can escape container isolation. The `SYS_ADMIN` capability combined with `hostPath` mounts enables full node compromise. Containers without read-only root filesystems can be used for persistence. Missing security contexts across a namespace indicate no enforcement of pod security standards.

### Verification Commands

```bash
# Check Pod Security Admission labels on namespaces
kubectl get namespaces -o json | \
  jq '.items[] | {name: .metadata.name, labels: (.metadata.labels // {} | with_entries(select(.key | startswith("pod-security"))))}'

# Find privileged containers
kubectl get pods --all-namespaces -o json | \
  jq '.items[] | select(.spec.containers[]?.securityContext?.privileged == true) | {ns: .metadata.namespace, pod: .metadata.name}'

# Find pods running as root
kubectl get pods --all-namespaces -o json | \
  jq '.items[] | select(.spec.containers[]?.securityContext?.runAsUser == 0 or .spec.securityContext?.runAsUser == 0) | {ns: .metadata.namespace, pod: .metadata.name}'

# Find pods with hostPID, hostNetwork, or hostIPC
kubectl get pods --all-namespaces -o json | \
  jq '.items[] | select(.spec.hostPID == true or .spec.hostNetwork == true or .spec.hostIPC == true) | {ns: .metadata.namespace, pod: .metadata.name, hostPID: .spec.hostPID, hostNet: .spec.hostNetwork, hostIPC: .spec.hostIPC}'

# Find containers with dangerous capabilities
kubectl get pods --all-namespaces -o json | \
  jq '.items[] | select(.spec.containers[]?.securityContext?.capabilities?.add[]? == "SYS_ADMIN" or .spec.containers[]?.securityContext?.capabilities?.add[]? == "NET_RAW") | {ns: .metadata.namespace, pod: .metadata.name}'

# Find hostPath volume mounts
kubectl get pods --all-namespaces -o json | \
  jq '.items[] | select(.spec.volumes[]?.hostPath != null) | {ns: .metadata.namespace, pod: .metadata.name, paths: [.spec.volumes[] | select(.hostPath != null) | .hostPath.path]}'
```

## Network Policies

### Attack Surface

Without NetworkPolicy resources, all pods in a cluster can communicate with all other pods (default allow-all). This enables lateral movement from a compromised pod to any service in the cluster, including databases, internal APIs, and management interfaces. Namespaces without deny-all ingress policies are open to cross-namespace traffic.

### Verification Commands

```bash
# List namespaces with and without NetworkPolicies
kubectl get networkpolicies --all-namespaces -o json | \
  jq '[.items[].metadata.namespace] | unique'

# Check for default deny ingress in each namespace
kubectl get networkpolicies --all-namespaces -o json | \
  jq '.items[] | select(.spec.ingress == null and .spec.podSelector == {}) | {ns: .metadata.namespace, name: .metadata.name}'

# List all namespaces and compare with those that have policies
kubectl get namespaces -o jsonpath='{.items[*].metadata.name}'

# Check exposed services (LoadBalancer, NodePort)
kubectl get services --all-namespaces --field-selector spec.type=LoadBalancer -o json | \
  jq '.items[] | {ns: .metadata.namespace, name: .metadata.name, ports: .spec.ports, lb: .status.loadBalancer}'

kubectl get services --all-namespaces --field-selector spec.type=NodePort -o json | \
  jq '.items[] | {ns: .metadata.namespace, name: .metadata.name, ports: [.spec.ports[].nodePort]}'

# Check for exposed Kubernetes dashboard
kubectl get deployments --all-namespaces | grep -i dashboard
kubectl get services --all-namespaces | grep -i dashboard
```

### Evidence Logging

```bash
ensphere evidence log \
  --probe-type cloud_k8s --technique cli_verification \
  --url "k8s://CLUSTER/namespace/NAMESPACE" \
  --result confirmed --session 7 \
  --file ./ensphere-pentest/07-cloud/evidence.jsonl \
  --notes "Namespace has no NetworkPolicy — unrestricted pod-to-pod communication"
```

## Service Mesh

### Attack Surface

Service meshes (Istio, Linkerd) provide mTLS and authorization policies, but misconfigurations can leave gaps. Permissive mTLS mode (`PERMISSIVE` in Istio) accepts both plaintext and encrypted traffic, allowing an attacker on the network to intercept unencrypted communications. Missing AuthorizationPolicy resources leave all traffic allowed by default. Sidecar injection may not be enforced in all namespaces.

### Verification Commands

```bash
# Check if Istio is installed
kubectl get namespaces -l istio-injection=enabled
kubectl get pods -n istio-system

# Check PeerAuthentication (mTLS mode)
kubectl get peerauthentication --all-namespaces -o json | \
  jq '.items[] | {ns: .metadata.namespace, name: .metadata.name, mode: .spec.mtls.mode}'

# Check for PERMISSIVE mode (allows plaintext)
kubectl get peerauthentication --all-namespaces -o json | \
  jq '.items[] | select(.spec.mtls.mode == "PERMISSIVE") | {ns: .metadata.namespace, name: .metadata.name}'

# Check AuthorizationPolicy resources
kubectl get authorizationpolicy --all-namespaces -o json | \
  jq '.items[] | {ns: .metadata.namespace, name: .metadata.name, action: .spec.action}'

# Check for namespaces without sidecar injection
kubectl get namespaces -o json | \
  jq '.items[] | select(.metadata.labels["istio-injection"] != "enabled") | .metadata.name'

# Linkerd checks
kubectl get namespace -l linkerd.io/inject=enabled 2>/dev/null
linkerd check 2>/dev/null
```

### Evidence Logging

```bash
ensphere evidence log \
  --probe-type cloud_k8s --technique cli_verification \
  --url "k8s://CLUSTER/peerauthentication/POLICY_NAME" \
  --result confirmed --session 7 \
  --file ./ensphere-pentest/07-cloud/evidence.jsonl \
  --notes "Istio PeerAuthentication uses PERMISSIVE mode — plaintext traffic accepted alongside mTLS"
```

## Secrets Management

### Attack Surface

Kubernetes Secrets are base64-encoded (not encrypted) by default and stored in etcd. Any principal with `get secrets` permission in a namespace can read all secrets. Secrets mounted as environment variables appear in `/proc/<pid>/environ` and container inspection output. External secrets operators (AWS Secrets Manager, HashiCorp Vault, Azure Key Vault) may have overpermissive sync policies.

### Verification Commands

```bash
# List all secrets across namespaces (types reveal what they contain)
kubectl get secrets --all-namespaces -o json | \
  jq '.items[] | {ns: .metadata.namespace, name: .metadata.name, type: .type}'

# Check for secrets mounted as environment variables (visible in process listing)
kubectl get pods --all-namespaces -o json | \
  jq '.items[] | select(.spec.containers[]?.env[]?.valueFrom?.secretKeyRef != null) | {ns: .metadata.namespace, pod: .metadata.name, secrets: [.spec.containers[].env[]? | select(.valueFrom?.secretKeyRef != null) | .valueFrom.secretKeyRef.name]}'

# Check for ExternalSecret resources (external-secrets operator)
kubectl get externalsecrets --all-namespaces 2>/dev/null -o json | \
  jq '.items[] | {ns: .metadata.namespace, name: .metadata.name, store: .spec.secretStoreRef}'

# Check SecretStore/ClusterSecretStore configurations
kubectl get secretstores --all-namespaces 2>/dev/null -o json
kubectl get clustersecretstores 2>/dev/null -o json

# Check SealedSecrets (Bitnami)
kubectl get sealedsecrets --all-namespaces 2>/dev/null

# Check if encryption at rest is configured (provider-specific)
# EKS: check KMS encryption
# GKE: application-layer encryption is optional
# AKS: check etcd encryption
```

### Evidence Logging

```bash
ensphere evidence log \
  --probe-type cloud_secrets --technique cli_verification \

  --notes "Database credentials exposed as environment variables — visible in pod spec and /proc"
```

## etcd Access

### Attack Surface

Direct etcd access bypasses all Kubernetes API authentication and authorization. etcd backups contain all cluster state including Secrets in plaintext. Self-managed clusters may expose etcd on port 2379 without client certificate authentication. Cloud-managed clusters (EKS, GKE, AKS) manage etcd internally, but etcd encryption at rest may not be enabled.

### Verification Commands

```bash
# Check if etcd is directly accessible (self-managed clusters)
kubectl get pods -n kube-system | grep etcd
kubectl describe pod etcd-MASTER_NODE -n kube-system 2>/dev/null | grep -E 'listen-client-urls|client-cert-auth|trusted-ca-file'

# Check etcd encryption configuration
kubectl get apiserver -o json 2>/dev/null | \
  jq '.items[]?.spec.encryption'

# For self-managed: check if etcd port is exposed
# (requires network access to control plane nodes)
# Port 2379 (client) and 2380 (peer) should not be publicly accessible

# Check for etcd backup CronJobs (backups may contain plaintext secrets)
kubectl get cronjobs --all-namespaces | grep -i etcd

# Cloud-managed etcd encryption checks are provider-specific:
# AWS EKS: aws eks describe-cluster --query 'cluster.encryptionConfig'
# GCP GKE: gcloud container clusters describe --query 'databaseEncryption'
# Azure AKS: etcd is always encrypted at rest with platform-managed keys
```

### Evidence Logging

```bash
ensphere evidence log \
  --probe-type cloud_secrets --technique cli_verification \
  --url "k8s://CLUSTER/etcd" \
  --result confirmed --session 7 \
  --file ./ensphere-pentest/07-cloud/evidence.jsonl \
  --notes "etcd accessible on port 2379 without client certificate authentication"
```

## Admission Controllers

### Attack Surface

Without admission controllers, there is no enforcement of security policies at deployment time. Pods with privileged containers, host mounts, or escalated capabilities can be deployed unchecked. OPA/Gatekeeper and Kyverno provide policy-as-code enforcement, but misconfigured policies, audit-only mode, or exempted namespaces leave gaps.

### Verification Commands

```bash
# Check OPA/Gatekeeper installation
kubectl get pods -n gatekeeper-system 2>/dev/null
kubectl get constrainttemplates 2>/dev/null -o json | \
  jq '.items[] | .metadata.name'

# List Gatekeeper constraints and their enforcement action
kubectl get constraints 2>/dev/null -o json | \
  jq '.items[] | {kind: .kind, name: .metadata.name, action: .spec.enforcementAction, violations: .status.totalViolations}'

# Check for audit-only constraints (enforcementAction: dryrun or warn)
kubectl get constraints 2>/dev/null -o json | \
  jq '.items[] | select(.spec.enforcementAction != "deny") | {kind: .kind, name: .metadata.name, action: .spec.enforcementAction}'

# Check exempted namespaces
kubectl get constraints 2>/dev/null -o json | \
  jq '.items[] | {kind: .kind, name: .metadata.name, excludedNamespaces: .spec.match.excludedNamespaces}'

# Check Kyverno installation
kubectl get pods -n kyverno 2>/dev/null
kubectl get clusterpolicies 2>/dev/null -o json | \
  jq '.items[] | {name: .metadata.name, validationFailureAction: .spec.validationFailureAction}'

# Check for Kyverno policies in audit mode
kubectl get clusterpolicies 2>/dev/null -o json | \
  jq '.items[] | select(.spec.validationFailureAction == "Audit") | .metadata.name'

# Check PodSecurityPolicy (deprecated in 1.25, removed in 1.25+)
kubectl get podsecuritypolicies 2>/dev/null

# Check ValidatingWebhookConfigurations
kubectl get validatingwebhookconfigurations -o json | \
  jq '.items[] | {name: .metadata.name, webhooks: [.webhooks[]?.name]}'

# Check MutatingWebhookConfigurations
kubectl get mutatingwebhookconfigurations -o json | \
  jq '.items[] | {name: .metadata.name, webhooks: [.webhooks[]?.name]}'
```

## Cross-Correlation with Web Findings

Kubernetes-specific attack chains that combine web vulnerabilities with cluster misconfiguration:

| Web Finding | K8s Finding | Combined Attack |
|-------------|-------------|-----------------|
| SSRF (Session 06) | Service account token mounted | SSRF to `https://kubernetes.default.svc/api/v1/namespaces/NAMESPACE/secrets` with SA token to read secrets |
| SSRF (Session 06) | No NetworkPolicy | SSRF to internal cluster services (databases, caches, APIs) |
| RCE / CMDi (Session 02) | Privileged container | Command execution in privileged container to escape to node |
| RCE / CMDi (Session 02) | hostPath mount | Command execution to read/write host filesystem via mount |
| LFI (Session 02) | SA token auto-mounted | LFI to `/var/run/secrets/kubernetes.io/serviceaccount/token` to steal SA token |
| Auth bypass (Session 03) | Overprivileged SA | Auth bypass to application whose SA has cluster-admin |

### Service Account Token Verification

```bash
# Check which pods have auto-mounted service account tokens
kubectl get pods --all-namespaces -o json | \
  jq '.items[] | select(.spec.automountServiceAccountToken != false and (.spec.serviceAccountName // "default") != "default") | {ns: .metadata.namespace, pod: .metadata.name, sa: .spec.serviceAccountName}'

# For each SA, check its permissions
kubectl auth can-i --list --as=system:serviceaccount:NAMESPACE:SA_NAME
```
