Ensphere Production-Grade Hardening Plan

A standalone execution plan for closing the 10 identified maturity gaps in the Ensphere repository. The plan is written for an AI coding agent, but keeps human review gates explicit so the project improves in reliability, maintainability, and auditability without diluting its core design principle.

Summary

Ensphere already has a strong core: the verify layer returns raw measurements, scope validation prevents accidental probing outside authorization, evidence is hash-chained, payloads are generated from YAML seeds, and the main Go test suite passes. The remaining work is about making that quality repeatable, observable, and enforceable.

Current Strengths

  • Deterministic measurement model in verify outputs.
  • Mandatory in-scope checks for verify commands.
  • Payload database generated from YAML with enum validation.
  • Evidence JSONL writer with tamper-evident hash chain.
  • Meaningful tests in core packages such as verify, evidence, openapi, cvss, and callback.

Production-Grade Target

  • Every push and pull request runs repeatable quality gates.
  • CLI behavior is tested at the binary boundary, not only through internal packages.
  • Evidence IDs and classification ownership are consistent everywhere.
  • Generated assets cannot silently drift from source data.
  • Static scanning is accurately framed, tested, and incrementally improved.

Non-negotiable principle: Ensphere code may measure, compare, hash, count, validate, redact, and calculate from fixed inputs. It must not assign exploitability, confidence, confirmed status, or security judgment unless the value is explicitly recorded as external AI/human analysis.

Agent Protocol

The work should be performed as small, reviewable changes. The agent must preserve existing user changes, run targeted tests before broad tests, and keep generated artifacts synchronized with their sources.

Preflight Commands

git status --short --branch
go version
cd cli && go list ./...
make test
make smoke
cd cli && go test -race -short ./internal/verify/

Worktree Rules

  • Do not revert changes you did not make.
  • Keep generated changes intentional and documented.
  • Prefer scoped commits by gap or phase.
  • Use apply_patch for manual edits.

Test Rules

  • Run package-level tests after each focused change.
  • Run make test before finishing each phase.
  • Run make smoke after build or generated DB changes.
  • Run race checks for concurrency or verify changes.

Review Rules

  • Confirm CLI output remains JSON where promised.
  • Confirm verify commands remain measurement-only.
  • Confirm scope and max-risk gates execute before requests.
  • Confirm docs match behavior.

Definition of Done

Gap Workstreams

Each workstream includes implementation tasks, edge cases, acceptance criteria, validation commands, and suggested file areas. Complete P0 and P1 items first.

1. Add a CI Pipeline

Make quality gates automatic for every push and pull request.

Priority P0 Phase 1 CI/CD
Primary files.github/workflows/*.yml
Makefile
docs/testing.md

Implementation Plan

  1. Create .github/workflows/ci.yml.
  2. Install Go using go-version-file: cli/go.mod; fail fast if that version is unavailable.
  3. Cache Go modules and build cache using stable cache keys.
  4. Run go vet ./..., go test ./..., make smoke, and a short race test for internal/verify.
  5. Add a generated-artifact drift check by running make verify-generated.
  6. Document the CI gates in docs/testing.md.

Edge Cases

  • Go version uses 1.26.x, which may not exist on some public CI images when this plan is executed. CI must fail clearly; do not downgrade Go.
  • make smoke regenerates payloads.sqlite and checklist data, so CI must detect unintended drift.
  • Race tests can be slower; keep them short and package-scoped.
  • CI must run from repo root, while most Go commands run from cli/.

Suggested Workflow Skeleton

name: ci

on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: cli/go.mod
          cache-dependency-path: cli/go.sum
      - name: Verify packages
        working-directory: cli
        run: |
          go vet ./...
          go test ./...
          go test -race -short ./internal/verify/
      - name: Smoke
        run: make smoke
      - name: Generated artifact drift
        run: make verify-generated

Acceptance Criteria

2. Add Command-Layer Tests

Test the CLI as users experience it: flags, output, exit behavior, and command wiring.

Priority P0 Phase 3 CLI UX
Primary filescli/cmd/*
cli/cmd/*_test.go
cli/main.go

Current command functions frequently call os.Exit. That makes direct unit tests difficult. Use subprocess-based tests first so real binary behavior is locked before any command-handler refactor.

Implementation Plan

  1. Add subprocess tests that build or invoke the CLI for representative commands.
  2. Cover help output, required flag errors, invalid enum values, JSON output, and exit codes.
  3. Start with low-risk deterministic commands: payloads, cvss, template --list, checklist --list, compliance --list, openapi --file.
  4. Add one representative verify command test for scope failure and no network execution.
  5. Do not refactor command handlers in this workstream. Defer command-runner abstractions to Gap 7 after subprocess tests exist.

Edge Cases

  • Subprocess tests must isolate temp files and not write evidence into the repo root.
  • Tests must not depend on exact help text formatting except for important command names or flags.
  • JSON tests should parse output rather than string-compare pretty formatting.
  • Scope failure tests must prove no HTTP request is attempted.
  • Invalid arguments should return the intended code: usage/scope errors as 2, runtime failures as 3, root execution errors as documented.
  • Malformed --header values should be asserted as usage errors once header parsing is centralized.

Implementation Plan

  2. Add tests for sinks.ListCategories, sinks.GetCategory, and invalid category handling.
  3. Add tests for templates.ListTemplates, TemplateNames, and Materialize into a temp dir.

4. Fix Evidence ID Consistency

Ensure automated and manual evidence entries can be referenced reliably.

Priority P0 Phase 2 Evidence
Primary filesinternal/evidence/*
internal/verify/sqli.go
cmd/evidence_log.go
skills/*

Locked Decision

evidence.Writer assigns sequential EVID-XXX IDs at write time for entries missing an ID. Automated verify evidence must be directly referenceable without report-stage ID assignment.

Implementation Plan

  1. Extend Writer to recover the next sequence number from existing entries.
  2. If an entry has no ID, assign EVID-%03d.
  3. Update evidence log so it does not precompute IDs with NextID; let Writer.Write assign the ID.
  4. Preserve explicitly supplied IDs for manual log entries, but reject duplicate IDs deterministically.
  5. Update NextID to use max numeric ID, not just count, so malformed or filtered entries do not cause collisions.
  6. Add a standard-library lock file next to the evidence file, using exclusive create on <evidence>.lock, retry every 50 ms for up to 5 seconds, and cleanup on close.
  7. Add tests for empty file, missing file, existing entries, mixed ID/no-ID entries, duplicate IDs, append continuity, malformed lines, and two writer instances.
  8. Update skill and report docs to state automated evidence has IDs at write time.

Edge Cases

  • Existing evidence files may contain entries without IDs.
  • Existing files may have non-sequential IDs, such as EVID-001 and EVID-010.
  • Malformed lines are currently skipped; ID recovery must still be deterministic.
  • Concurrent writers can race on sequence numbers. The lock file must protect separate writer instances and separate processes.
  • Stale lock files should fail clearly after 5 seconds; do not wait forever and do not auto-delete the stale lock.
  • Hash computation must include the assigned ID and previous hash exactly once.

5. Clarify Judgment Boundary

Keep Ensphere as the measurement engine and make all classifications externally owned.

Priority P0 Phase 2 Product Integrity
Primary filescmd/evidence_log.go
internal/evidence/model.go
README.md
skills/SKILL.md
skills/shared/*

Implementation Plan

  1. Treat Entry.Result as factual measurement stage only.
  2. Restrict result values to baseline, probe, payload, control, callback, and manual_note for this pass.
  3. Add centralized validation for Entry.Result in the evidence package and update verify evidence writes to use the allowed values.
  4. Move detailed stage names such as true_probe, false_probe, high_priv, low_priv, injection, and verify into Notes instead of Result.
  5. Do not add analysis_status, analysis_source, or analysis_at fields in this hardening pass. Classification remains in AI/human reports.
  6. Update evidence log examples so they do not imply the CLI generated confirmed or safe.
  7. Search all code and docs for confirmed, potential, safe, confidence, and status in CLI-owned contexts.
  8. Add tests or lints that fail if verify result JSON gains forbidden fields such as status, confidence, or confirmed.

Edge Cases

  • CVSS severity is deterministic from user-supplied metrics and is allowed, but docs should explain the user supplies the security judgment inputs.
  • Cloud parser ingests third-party severity from Prowler/Trivy. It should label that as source-provided, not Ensphere-generated.
  • Manual evidence logging must not record external conclusions in Entry.Result; use reports for conclusions.
  • Skill files may instruct the AI to classify. That is allowed because the AI layer owns judgment.
  • Existing evidence files with old result values should still be readable, but new writes must use the allowed values.

6. Upgrade and Reframe Static Scanner

Make the scanner honest, tested, and incrementally stronger without pretending it is full SAST.

Priority P1 Phase 3 Scanner
Primary filesinternal/scan/*
internal/sinks/data/sinks.yaml
cmd/scan.go
README.md

Locked Scope

Do Track A only in this hardening pass: keep the scanner regex-based, make it honest, tested, bounded, and redacted. Do not implement AST scanning yet.

Implementation Plan

  1. Add tests for RunScan, scanFile, absence rules, excludes, and sorting.
  2. Add a field like engine: "regex" or analysis_depth: "pattern_match" in scan output.
  3. Document that matches are leads for AI/human review, not confirmed vulnerabilities.
  4. Redact scanner context by default using shared redaction logic so matched tokens or secrets are not dumped.
  5. Add --context-lines with bounds: default 2, minimum 0, maximum 5.
  6. Add tests that compile every embedded sink regex and fail on invalid patterns.

Edge Cases

  • Binary files or huge generated files should be skipped or bounded.
  • Symlink loops should not cause infinite traversal.
  • Regexes may be invalid in sink YAML; invalid patterns must fail in tests, not only warn at runtime.
  • Scanner context can include secrets; redact sensitive values in output.
  • Absence rules can produce false positives when security settings are declared outside the fixed window.

7. Reduce Verify Command Boilerplate

Keep command files simple while removing repeated error handling, JSON encoding, and header parsing.

Priority P2 Phase 3 Maintainability
Primary filescmd/verify_*.go
cmd/root.go
cmd/helpers.go

Implementation Plan

  1. Add command helper functions for header parsing, JSON encoding, and verify error-to-exit-code handling.
  2. Refactor 2 or 3 representative verify commands first: one simple command, one token command, one multi-URL command.
  3. Run tests and compare help/output behavior before refactoring the rest.
  4. Move repeated defaults into shared constants where appropriate.
  5. Do not over-abstract command-specific flags into a complex framework unless repetition remains painful after small helpers.

Required Helper Surface

func parseHeaders(raw []string) map[string]string
func encodeJSON(out interface{}) error
func exitForVerifyError(err error) int
func runVerify(fn func() (*verify.ProbeResult, error)) error

Edge Cases

  • Header values may contain colons. Split only once.
  • Invalid header syntax must be rejected as a usage error with exit code 2.
  • RunE handlers that call os.Exit are hard to test. A helper can preserve behavior while exposing testable logic.
  • Some commands have multiple URLs, such as CSV injection submit/export and RLS project URLs.
  • Exit codes must remain backward compatible.

8. Add CLI Golden and Schema Tests

Protect the public JSON contract consumed by AI agents, scripts, and reports.

Priority P1 Phase 1 Contracts
Primary filescli/testdata/*
cmd/*_test.go
internal/verify/contracts_test.go

Implementation Plan

  1. Create representative semantic JSON tests for payloads, cvss, template --list, checklist --list, compliance --list, openapi, evidence query, and one verify output.
  2. Parse JSON and assert fields, types, counts, schema versions, and stable invariants. Do not add a JSON Schema dependency in this pass.
  3. Use exact golden fixtures only for stable, intentionally frozen sample outputs.
  4. Add a forbidden-field assertion for verify outputs: no status, confidence, confirmed, safe, or potential.
  5. Document schema versioning rules: breaking changes require version bump.

  • Pretty indentation should not be the main contract; parsed JSON shape is the contract.
  • Version fields should be asserted where present.
  • Schema tests should cover empty result sets and invalid filters.
  • Timestamp and duration values should be asserted by format/type, not exact value.

9. Tighten Generated Payload DB Workflow

Prevent YAML seeds, embedded SQLite, enum validation, and docs from drifting.

Priority P1 Phase 1 Generated Assets
Primary filesassets/seeds/*.yaml
tools/seedgen
internal/payloads
README.md
docs/testing.md

Implementation Plan

  1. Add a make verify-generated target that regenerates seeds and checklist data, then checks git diff --exit-code.
  2. Add seedgen tests for minimal fixtures, enum failures, duplicate IDs, invalid risk, missing required fields, and placeholder JSON.
  3. Add a command or test that reports payload counts by vuln type and checks docs canaries.
  4. Ensure seedgen output is deterministic: sort file inputs, use a fixed generated timestamp, keep SQLite pragmas stable, and vacuum consistently.
  5. Update make checklists so it deletes cli/internal/checklist/data/ before copying current checklist files.
  6. Add CI coverage for make verify-generated.

Edge Cases

  • Timestamps in generated DB can cause non-deterministic binary changes if regenerated at different times; use a fixed timestamp.
  • SQLite file bytes may vary by SQLite version or pragma behavior; CI should use the same Go/SQLite dependency versions from go.sum.
  • Two payloads can generate the same ID if vuln type, technique, surface, and payload match.
  • Docs may reference total payload count, vuln type count, or supported DB engines in multiple places.
  • Checklist copy target can hide stale files if removed source files are not deleted first.
