Ensphere Production Hardening Plan

Preserve the completed design-boundary cleanup, then prove methodology quality and release reliability with reproducible evidence.

Reviewed 18 July 2026 · Current working tree · No compatibility track
Verdict

The design-boundary P0 work is complete, but Ensphere is not production-proven yet. Cloud and template outputs are factual, Session 10 is human-authorized and default-off, current-only terminology is consistent, fake reports are gone, and a benchmark protocol exists. The remaining work is empirical evaluation and engineering hardening.

Production grade means conformance before polish

Ensphere has CI, meaningful tests, deterministic generated assets, strict runner contracts, evidence integrity, report gates, factual cloud output, observation-only template metadata, and an exact human-authorization contract for optional impact validation.

A passing test suite proves the implemented behavior is stable. It does not prove the implemented behavior respects the intended product boundary.

No release should describe the methodology as effective across target classes until pinned blind benchmark runs have measured both missed known conditions and unsupported report claims.

  • Cloud IAM records permission actions; compute and storage preserve provider endpoint, authentication, ingress, and access-control settings without Ensphere-owned exposure or escalation verdicts.
  • Embedded Python metadata lists observation fields rather than threshold-based success signals, and scripts emit measurements rather than acceptance verdicts.
  • run validate-impact, run impact-ready, impact_validation, and 10-impact-validation/ replace misleading exploit-oriented runner terminology without aliases. Separate strict authorization records bind each approved machine-readable plan SHA-256; the pre-execution and final gates check executor, environment, ordered actions, elapsed time, rollback, and cleanup proof.
  • Session 10 requires a passing Session 09 report gate, mandatory cleanup accounting, exact-plan authorization evidence, a named human or AI executor, and executor-specific evidence.
  • Session 11 preserves every Session 09 status and attaches the optional outcome as a separate dimension.
  • Synthetic sample reports were deleted. Benchmark reports remain local until backed by a reviewable evidence workspace.
  • The skill examples and current runner schemas use strict current contracts only.

Regression criterion: deterministic output describes observable configuration or behavior; a different defensible analyst judgment does not contradict the CLI.

P1: prove reliability beyond unit contracts

5. Add end-to-end workspace fixtures

Create small reproducible workspaces covering a complete Sessions 01–09 run, limited/blocked/not-applicable sessions, invalid evidence chains, unsafe paths, imported leads, and optional human-authorized outcomes. Assert both accepted and rejected states.

6. Fuzz the parsers and boundaries

Add fuzz or property tests for strict YAML decoding, evidence JSONL, redaction, citation paths, OpenAPI input, external import formats, and selected-finding/outcome merging. Prioritize panics, path escapes, silent truncation, duplicate identity, and secret leakage over coverage percentages.

7. Define honest redaction guarantees

The current redactor covers bearer/JWT forms and selected sensitive query parameters; it is not a general PII detector. Document the exact automatic coverage, add representative secret fixtures, and keep manual publication review mandatory.

8. Build reproducible releases

  • Versioned binaries for supported platforms with checksums and provenance.
  • Software bill of materials and dependency/license inventory.
  • Installation and upgrade smoke tests using the exact released artifacts.
  • A compatibility declaration for binary plus skill revisions—current pairings only, not historical migrations.
  • A release checklist that references CI results and generated-asset cleanliness rather than browser-local state.

9. Evaluate methodology and report quality

Run the product-plan evaluation corpus and review false claims, missed known conditions, coverage gaps, reproducibility, and engineering usefulness. A report gate validates completeness of artifacts; it cannot validate whether the analyst made the best judgment.

Definition of production-ready

Ensphere is production-ready when all of the following are true:

  • The deterministic layer emits facts and source claims without heuristic security judgments.
  • The active skill, examples, runner, CLI reference, and technical specification describe the same current contract.
  • Session 09 is complete and decision-ready without Sessions 10–11.
  • Session 10 cannot progress without a passing assessment gate, exact selection, actual human approval, environment acknowledgement, bounded plans, and cleanup policy.
  • Session 11 preserves Session 09 statuses and visibly limits its claims to selected findings.
  • End-to-end fixtures cover successful, limited, blocked, malformed, and adversarial workspace states.
  • Methodology evaluation demonstrates useful reports across materially different target shapes and records known misses honestly.
  • Release artifacts are reproducible, attributable, installable, and paired with the matching skill revision.
  • All required CI, race, smoke, generated-drift, skill, link, and formatting checks pass from a clean checkout.

No backward compatibility requirement is part of this definition. The current contract is the product.
